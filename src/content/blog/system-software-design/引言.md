# 系统软件设计笔记：引言

这不是一份孤立的设计模式清单，也不以记住 `Factory`、`Handler` 或 `Traits`
的定义为目标。它是一门为自己构建的 **系统软件设计课程**：从 C++ 与系统工程中
常见的真实代码出发，理解代码为什么会变得难读、难改、难测，再学习如何在约束中做出
更合适的设计。

这里的“系统软件”包括运行时、通信库、推理服务、资源管理、异步任务和硬件后端等场景。
它们通常同时面对性能、并发、资源生命周期和多实现后端的压力。因此，设计并不是把类
拆得越多越好；更重要的是让**职责、控制权、数据流和资源边界**保持清楚。

## 想建立的能力

学习完成后，希望获得的不是“代码里用了哪些模式”，而是下面这种判断力：

- 看到 `getInstance()`、全局 `Manager`、层层转发的 `Handler`，能判断它们解决了什么，
  又可能掩盖了什么依赖与生命周期问题。
- 面对“替换一个算法或后端要改多少地方”的问题，能定位变化的边界，并选择运行时策略、
  编译期策略或更直接的实现。
- 阅读 CUDA、MPI、PyTorch、vLLM、NCCL 等工程时，能把 `Runtime`、`Context`、
  `Scheduler`、`Executor`、`Backend` 等名称还原为具体的架构职责。
- 重构时不只套模式，而是能说明：改动解决了哪个瓶颈，增加了哪些复杂度，又在哪些规模下
  不值得采用。

## 学习方法：从坏代码到设计取舍

每个主题尽量沿用同一条推理链，而不是先背诵抽象概念：

```mermaid
flowchart LR
    A["真实坏代码"] --> B["识别 Code Smell"]
    B --> C["定位根因"]
    C --> D["建立设计原则"]
    D --> E["选择设计工具"]
    E --> F["逐步重构"]
    F --> G["评估取舍与边界"]
```

其中，**Code Smell（代码异味）不是结论，而是线索**。例如 `Singleton` 并不天然错误；
它往往是在“方便访问”“统一初始化”等局部需求下出现的。真正需要追问的是：谁依赖它？
谁拥有它？测试时能否替换它？它的初始化和销毁顺序是否安全？

同样，一串抽象层也不必然代表架构良好：

```text
MPI_Send
  ↓
MPIHandler::send
  ↓
CommunicationManager::send
  ↓
CommunicationService::send
```

如果每一层都只做无语义的转发，那么它们隐藏的不是复杂度，而是控制流和依赖关系。
反过来，若某一层确实承担了协议转换、资源管理、错误恢复或调度策略，它才可能是有价值的
抽象。笔记会始终把这种**意图、实现、约束与使用场景**分开讨论。

## 学习地图

整个系列按问题的来源逐步展开，而非按设计模式名称排列。

| 模块 | 关注的问题 | 代表主题 |
|---|---|---|
| 对象、依赖与生命周期 | 谁拥有资源？对象何时有效？模块知道得是否过多？ | Ownership、Lifetime、RAII、Dependency Injection、Handle / View |
| 抽象与接口边界 | 一层封装是否真的形成了抽象？实现差异如何隔离？ | Interface、Facade、Adapter、Backend、PImpl、Leaky Abstraction |
| 变化与扩展 | 什么会变？替换策略或后端的成本在哪里？ | Policy vs Mechanism、Strategy、Factory、Registry、Plugin、Configuration |
| 控制流设计 | 谁决定做什么、何时做、由谁执行？ | Handler、Dispatcher、Scheduler、Executor、Command、Pipeline、State Machine |
| C++ 类型设计 | 差异应在编译期还是运行时解决？ | Composition、Template、Traits、Concepts、Policy Class、CRTP、Type Erasure |
| 状态与并发 | 状态归谁管理？线程如何共享与协作？ | Thread Ownership、Message Passing、Task Queue、Async API、Cancellation、Backpressure |
| 子系统架构 | 工程中的基础组件各自承担什么角色？ | Runtime、Context、Driver、Memory Pool、Transport、Protocol、Service |
| 架构退化 | 局部合理的改动如何累积成难以维护的系统？ | God Object、Manager Hell、Boolean Hell、循环依赖、Temporal Coupling |

这些主题之间并非独立。例如，`Context`、`Manager`、`Singleton` 与异步资源管理最终都会回到
三个基础问题：**所有权（Ownership）、生命周期（Lifetime）与依赖（Dependency）**。因此，
系列会从这三者开始，而不是从“Singleton 好不好”开始。

## 如何阅读与记录

每篇笔记尽量围绕一个具体问题，使用统一结构：

1. **问题从哪里来**：给出一段真实或最小化的代码。
2. **代码异味与根因**：说明不适感来自哪里，而不是直接贴上模式标签。
3. **原则与设计词汇**：建立必要的概念边界，例如唯一所有权、借用、策略与机制分离。
4. **重构过程**：以小步改动展示结构如何变化，并说明每一步解决的问题。
5. **最终设计与取舍**：明确适用条件、成本与不应过度设计的场景。
6. **真实工程对照**：回到 CUDA、MPI、PyTorch、vLLM 等项目中验证这一设计如何落地。
7. **审查清单**：沉淀为以后阅读代码或 Code Review 时可重复使用的问题。
8. **练习题**：用本章的概念判断一小段新代码或接口；题目优先考察设计理由和边界，而非术语记忆。
